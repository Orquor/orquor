The verifier is the least understood component of the ACTO architecture, and the one that separates safe clinical AI from everything else. Here is how we design them, function by function.

A verifier is a deterministic function that takes a source utterance and a translated output and returns a pass/fail result with a weighted score. The function is not a machine-learning model. It is a set of rules, checks, and structured queries. This matters because it is auditable in a way a model prediction is not.

The design discipline has four rules.

**Rule 1 — Atomicity.** One verifier tests one property. V1 checks that numeric dosages in the source appear identically in the translation. V2 checks that dosage units (mg, mcg, IU) are preserved. V3 checks that drug names map to the correct generic in the target language. Three separate verifiers because a composite verifier that bundles all three would collapse three failure modes into one error message. A clinician who sees "V1-V3 composite failed" cannot act on that. A clinician who sees "V2 failed: mcg became mg" can issue a correction immediately.

**Rule 2 — Weighting by clinical consequence.** Every verifier carries a weight from 1 to 5. Catastrophic failures (dosage magnitude change, drug-name substitution, allergy omission) carry weight 5. They block the translation and escalate to the human interpreter. Moderate failures (register drift, terminology inconsistency within a session) carry weight 3. They trigger a second-pass MT before escalating. Stylistic failures (minor fluency gaps that do not affect clinical meaning) carry weight 1. They are logged and surfaced in the post-session report but do not block the translation.

**Rule 3 — Negative verifiers are mandatory.** A verifier suite that only checks that the correct information is present — dosage preserved, drug name correct, allergy noted — is insufficient. It does not detect that disallowed information has leaked into the translation. V4 in the current Orquor suite is a negative verifier: no excluded names (patient names, clinician names, any PHI beyond what the source contains) appear in the translation output.

**Rule 4 — Version immutability.** Every verifier function carries a version number. When a verifier changes — because the clinical guideline underlying it was updated, or because a new edge case was discovered — the version increments. The audit log records which version of which verifier ran against each translation. A translation verified under suite v1.2 is auditable as such three years later, even after the suite has reached v2.7.

The current Orquor Clinical verifier suite has 60 verifiers. We are publishing the complete suite specification in the next whitepaper appendix (Q3 2026). The subset in Section 4 of the ACTO whitepaper on arXiv is representative and covers the catastrophic-weight tier.

If you are building verifier suites for any clinical AI application — translation, summarization, clinical decision support — the same four rules apply. The discipline is application-agnostic. The weights are application-specific.
